## 常见的信号

信号大致可以分为以下几类：

- **终止进程的信号**
- **暂停/继续进程的信号**
- **由程序错误（如内存访问违规）产生的信号**
- **由终端活动（如 Ctrl+C）产生的信号**
- **用户自定义的信号**

下面列出最常见和重要的信号，包括它们的**编号**、**默认行为**和**产生原因**。

------

### 最重要的信号（必须掌握）

| 信号名称    | 编号     | 默认行为  | 描述与产生原因                                               |
| :---------- | :------- | :-------- | :----------------------------------------------------------- |
| **SIGHUP**  | 1        | Terminate | **挂起（Hangup）**。当终端断开连接时发送给控制进程。也常用于通知守护进程**重新加载配置文件**（如 `nginx -s reload`）。 |
| **SIGINT**  | 2        | Terminate | **中断（Interrupt）**。由用户从键盘触发，通常是按下 **`Ctrl+C`**。用于优雅地终止前台进程。 |
| **SIGQUIT** | 3        | Core      | **退出（Quit）**。由用户从键盘触发，通常是按下 **`Ctrl+\`**。不仅终止进程，还会生成 **core dump** 文件（用于调试）。 |
| **SIGKILL** | 9        | Terminate | **杀死（Kill）**。**立即强制终止**一个进程。此信号**不能被捕获、阻塞或忽略**。是确保进程被杀死的最后手段。 |
| **SIGTERM** | 15       | Terminate | **终止（Terminate）**。这是 `kill` 命令的**默认信号**。它请求进程**正常终止**，允许进程进行清理工作（如关闭文件、释放资源）后退出。 |
| **SIGSTOP** | 17,19,23 | Stop      | **停止（Stop）**。**暂停**一个进程的执行。与 SIGKILL 类似，它**不能被捕获或忽略**。通常由 shell 的作业控制使用（如 `Ctrl+Z` 发送的是 `SIGTSTP`）。 |
| **SIGCONT** | 18,19,25 | Continue  | **继续（Continue）**。让一个被 `SIGSTOP`、`SIGTSTP` 等暂停的进程**恢复运行**。 |

------

### 由程序错误产生的信号

| 信号名称    | 编号    | 默认行为  | 描述与产生原因                                               |
| :---------- | :------ | :-------- | :----------------------------------------------------------- |
| **SIGILL**  | 4       | Core      | **非法指令（Illegal Instruction）**。进程试图执行一条非法、未知或特权指令。通常由损坏的可执行文件或堆栈溢出引起。 |
| **SIGTRAP** | 5       | Core      | **陷阱跟踪（Trap）**。由断点指令或其他陷阱指令产生，**调试器**主要使用这个信号。 |
| **SIGABRT** | 6       | Core      | **中止（Abort）**。由 `abort()` 函数产生，通常表示程序检测到了严重错误并主动调用 abort 来终止自己。 |
| **SIGBUS**  | 7,10,10 | Core      | **总线错误（Bus error）**。非法内存访问，例如访问了未对齐的内存地址（如访问一个4字节整数，但其地址不是4的倍数）。 |
| **SIGFPE**  | 8       | Core      | **浮点异常（Floating-point exception）**。发生了致命的算术运算错误，如除以零、溢出等。 |
| **SIGSEGV** | 11      | Core      | **段错误（Segmentation fault）**。**最常见**的错误信号之一。表示进程进行了**无效的内存引用**，如访问未分配的内存、向只读内存写入数据等。 |
| **SIGPIPE** | 13      | Terminate | **管道破裂（Broken pipe）**。向一个没有读者的管道（或套接字）进行写操作。常见于网络连接中，一端已经关闭，另一端仍在发送数据。 |

### 其他常见信号

| 信号名称    | 编号     | 默认行为  | 描述与产生原因                                               |
| :---------- | :------- | :-------- | :----------------------------------------------------------- |
| **SIGALRM** | 14       | Terminate | **闹钟信号（Alarm clock）**。由 `alarm()` 或 `setitimer()` 函数设置的计时器超时后产生。 |
| **SIGCHLD** | 17,20,18 | Ignore    | **子进程状态改变（Child status has changed）**。当**子进程停止、恢复或退出**时，内核会向其父进程发送此信号。这对于父进程回收子进程资源（避免僵尸进程）至关重要。 |
| **SIGTSTP** | 18,20,24 | Stop      | **终端停止（Terminal stop）**。由用户从键盘触发，通常是按下 **`Ctrl+Z`**。用于**暂停**一个前台进程，但可以被程序捕获和处理。 |
| **SIGTTIN** | 21,21,26 | Stop      | **后台进程读终端（Background read from tty）**。当一个后台进程试图从终端读取数据时，终端驱动程序会发送此信号，通常会暂停该后台进程。 |
| **SIGTTOU** | 22,22,27 | Stop      | **后台进程写终端（Background write to tty）**。类似 SIGTTIN，但当后台进程试图向终端写入数据时产生。 |
| **SIGUSR1** | 10,30,16 | Terminate | **用户自定义信号 1**。**没有固定含义**，留给程序员自定义使用。常用于应用程序内部通信，如通知进程执行特定操作（重新打开日志文件）。 |
| **SIGUSR2** | 12,31,17 | Terminate | **用户自定义信号 2**。同上，另一个用户自定义信号。           |

### 如何使用这些信号？

## select 与 poll 与 epoll 的有什么区别

### select

**工作原理：**

1. 程序将要监视的文件描述符集合（读、写、异常）通过三个 `fd_set` 参数传入内核。
2. 内核会轮询检查所有被传入的fd，看是否有事件发生。
3. 当有事件发生或超时后，`select` 返回。
4. 返回后，程序必须**遍历所有fd**，通过 `FD_ISSET` 宏来判断具体是哪个fd就绪了。

**主要缺点：**

- **连接数限制**：`fd_set` 的大小是固定的（例如 1024），修改和重新编译内核才能改变。
- **性能问题**：每次调用都需要将整个fd_set从用户空间拷贝到内核空间，调用返回时再拷贝回来。当fd很多时，开销很大。
- **效率问题**：内核和应用程序在调用返回后都需要**线性扫描**所有fd，才能知道哪些fd就绪了。这是一个O(n)的复杂度。

**适用场景：** 跨平台编程（Windows也支持select），或者需要监视的fd数量非常少的情况。

------

### poll

**工作原理：**`poll` 解决了 `select` 的一些问题，但核心机制仍是轮询。

1. 程序提供一个 `pollfd` 结构体数组，每个结构体指定了要监视的fd和事件。
2. 内核轮询检查所有传入的fd。
3. 返回后，程序需要**遍历整个数组**，检查 `revents` 字段来判断哪些fd就绪。

**相对于select的改进：**

- **无最大数量限制**：使用动态数组，理论上只受系统最大文件描述符数量限制。
- **更精细的事件监视**：`pollfd` 结构体提供了更丰富的事件类型（如 `POLLRDHUP` 对端关闭连接）。

**仍然存在的缺点：**

- **性能问题**：和 `select` 一样，每次调用都需要将整个数组从用户空间拷贝到内核空间。
- **效率问题**：内核和应用程序仍然需要**线性扫描**所有fd，效率是O(n)。在连接数多但活跃连接少的情况下，效率很低。

**适用场景：** 比 `select` 稍好，但仍不适用于高性能、高并发的场景。

------

### epoll

`epoll` 是 Linux 2.6 引入的，专门为解决 `select` 和 `poll` 的缺陷而设计，是高性能网络服务器的基石。

**核心工作原理（与轮询完全不同）：**

1. **`epoll_create`**: 创建一个 `epoll` 实例，返回一个文件描述符。
2. **`epoll_ctl`**: 向 `epoll` 实例**注册/修改/删除**要监视的fd及其感兴趣的事件。**这个操作只执行一次**，而不是每次调用都传一遍。
3. **`epoll_wait`**: **等待事件发生**。调用时，它只返回就绪的文件描述符及其事件，而无需传递所有被监视的fd。应用程序无需遍历所有fd，直接处理这些就绪的fd即可。

**epoll 的优势：**

- **无描述符数量限制**：监视的fd数量上限是系统最大文件打开数。
- **高性能**：
  - **内核无需轮询**：epoll使用**回调机制**。内核在网络设备驱动程序中为每个fd注册回调函数，当某个fd有事件发生时，回调函数会将其加入一个就绪链表。
  - **`epoll_wait` 直接获取就绪fd**：调用 `epoll_wait` 时，只是检查这个就绪链表是否为空，如果不为空就直接返回内容。这使得其效率是 **O(1)**，与监听的fd总数无关，只与**活跃的fd数量**有关。
- **内存共享**：`epoll_wait` 返回时，使用 `mmap` 技术避免了内核和用户空间的内存拷贝。
- **支持边缘触发（ET）模式**：这是 `epoll` 的一大特色。
  - **水平触发（LT, Level-Triggered）**：**默认模式**。只要fd缓冲区中有数据可读，每次调用 `epoll_wait` 都会报告该事件。
  - **边缘触发（ET, Edge-Triggered）**：只在fd状态**发生变化时**（例如从无数据到有数据）报告一次。应用程序必须一次性读完所有数据（因为如果没读完，除非再有新数据到来，否则不会再次通知），这使得编程更复杂，但能减少系统调用次数，性能更高。

**适用场景：** Linux平台下，需要处理**大量并发连接**，且其中只有**少量是活跃连接**的高性能网络应用程序（如Nginx, Redis）。
