## STL 中包含哪些组件

STL 主要包含四类组件：

- 容器（Containers）：序列、关联、无序关联、容器适配
- 迭代器（Iterators）
- 算法（Algorithms）
- 函数对象（Function Objects）
- 适配器（Adapters）
- 空间配置器（Allocators）

序列容器：适合需要按顺序存储和访问数据的场景。
关联容器：适合需要通过键快速查找数据的场景，且键有序。
无序关联容器：适合需要通过键快速查找数据的场景，但不关心顺序。
容器适配器：适合需要特定行为（如栈、队列、优先级队列）的场景。

## 序列容器

**序列容器**：元素按线性顺序存储，支持按位置访问

| **容器**                     | **底层实现**      | **特点**                                                     | **适用场景**                 |
| :--------------------------- | :---------------- | :----------------------------------------------------------- | :--------------------------- |
| `std::vector`                | 动态数组          | - 随机访问快（O(1)） <br />- 尾部插入/删除快（O(1)均摊） <br />- 中间插入/删除慢（O(n)） | 需要高效随机访问 + 尾部操作  |

## 简述 vector 的实现原理

vector 是一种 **动态数组**，在内存中具有 **连续的存储空间**，支持快速随机访问，由于具有连续的存储空间，所以在插入和删除操作方面，效率比较慢。

当 vector 的大小和容量相等（size == capacity）时，如果再向其添加元素，那么 vector 就需要扩容。vector 容器扩容的过程需要经历以下 3 步：

1. 重新在堆上创建更大的动态数组，大小是原来的 2 倍；
2. 将旧内存空间中的数据，按原有顺序移动到新的内存空间中；
3. 最后将旧的内存空间释放。

扩容以后它的内存地址会发生改变



## 简述 deque 的实现原理

deque 是双端队列。

由多个 **固定大小的连续内存块（缓冲区）** 构成，每个缓冲区存储若干元素。通过中控器（`map`）维护这些缓冲区的指针，使使用者感知为“假连续”。

- 当 `map` 容量不足时，重新分配更大的空间（类似 `vector` 的 2 倍扩容），拷贝原有指针并释放旧 `map`。
- `map` 扩容不影响缓冲区内的数据（仅调整指针位置）

所谓的 map 是一小块连续的内存空间，其中的每个元素都是一个指针，指向另一段连续的内存空间，称作缓冲区。缓冲区才是 deque 的存储空间的主体。

**首尾操作高效**，时间复杂度 `O(1)`，中间操作较慢



## 简述 array 的实现原理

std::array 是一个固定大小的数组容器

- **编译时确定大小**，不可动态扩容。
- **栈上分配内存**（与 `vector` 不同，`vector` 在堆上动态分配）。
- **支持随机访问**，性能与原生数组几乎相同，但更安全（提供边界检查）。

为什么 `std::array` 的 `size()` 是 O(1)？

- 因为大小 `N` 是模板参数，编译期已知，直接返回常量。

如何避免 `std::array` 的越界访问？

- 使用 `at()` 替代 `operator[]`，或静态检查索引

时间复杂度：访问/修改 O(1)



## 简述 list 的实现原理

`std::list` 是 C++ STL 中的 **双向链表容器**，其核心特点是 **非连续内存存储、高效的插入/删除操作**，但 **不支持随机访问**。

`std::list` 的每个元素（节点）包含：

- **数据域**：存储用户数据（`T` 类型）。
- **前驱指针**（`prev`）：指向前一个节点。
- **后继指针**（`next`）：指向后一个节点。

优势：

- **任意位置插入/删除高效**：仅需修改指针，无元素移动。
- **适合频繁修改的场景**：如实时数据流处理。

std::list **任意位置高效插入/删除**：仅需修改指针，无需数据移动。

std::deque **高效随机访问**：通过计算分段位置直接访问元素。



## 简述 forward_list 的实现原理

`std::forward_list` 是 C++11 引入的 **单向链表** 容器，**适合高频插入/删除**：如实现轻量级任务队列或哈希表冲突链。

**Q1：为什么 `forward_list` 不提供 `size()`？**

- 为了极致轻量化，避免维护计数器（长度需遍历计算，不符合零开销抽象原则）。

**Q2：如何高效删除 `forward_list` 的当前节点？**

- 必须知道前驱节点，通过 `erase_after(prev_it)` 删除 `prev_it` 的后继节点。

**Q3：`forward_list` 与 `list` 如何选择？**

- 需要最小内存开销时选 `forward_list`；需要双向操作或稳定迭代器时选 `list`。

## 简述 `unordered_set`的实现原理

`std::unordered_set` 是 C++ STL 中的**无序关联容器**，用于存储**唯一元素**并支持**快速查找**（平均 O(1) 时间复杂度）。其底层基于**哈希表（Hash Table）**实现，核心原理如下：

- 将元素的键（Key）映射到一个固定大小的**哈希值**（`size_t` 类型）。
- C++ 默认使用 `std::hash<T>` 特化版本（如 `std::hash<int>`、`std::hash<std::string>`）。
- **自定义类型**需手动定义哈希函数：
- 哈希表由一个**桶数组**（`std::vector<std::forward_list<T>>`）组成。
- 每个桶存储一个链表（或类似结构），用于解决哈希冲突（链地址法）。
- **桶数量**（`bucket_count`）动态扩展，通常为质数以减少冲突。
- **链地址法**（Separate Chaining）：
  哈希到同一桶的元素以链表形式存储（C++ 标准未规定具体实现，但主流库如 GCC 使用单向链表）。
- **开放寻址法**（Open Addressing）：
  某些优化实现可能采用（如 Google 的 `dense_hash_set`）。

| **操作**             | **平均时间复杂度** | **最坏时间复杂度** | **说明**                       |
| :------------------- | :----------------- | :----------------- | :----------------------------- |
| **插入（`insert`）** | O(1)               | O(n)               | 哈希冲突极端时退化为链表遍历。 |
| **删除（`erase`）**  | O(1)               | O(n)               | 同上。                         |
| **查找（`find`）**   | O(1)               | O(n)               | 依赖哈希函数质量。             |
| **遍历**             | O(n)               | O(n)               | 需访问所有桶和链表。           |

## 迭代器失效原因，有哪些情况

迭代器失效是指迭代器在遍历容器过程中，由于容器的结构发生改变而导致迭代器指向的元素不再有效。

以下是导致迭代器失效的常见情况：

1. **插入和删除操作：** 当在容器中插入或删除元素时，可能会导致容器内存重新分配或元素位置的改变，这可能会使迭代器失效。
2. **清空容器：** 清空容器会使容器内的所有元素被删除，这样迭代器指向的元素就会失效。
3. **使用引起重新分配的操作：** 例如，在 `vector` 中使用 `push_back()` 添加元素时，如果超出了当前容量，可能会触发重新分配操作，从而使所有迭代器失效。
4. **排序操作：** 如果在排序过程中，容器的元素被移动了位置，迭代器可能会失效。

`set`和`map`的迭代器失效**最主要的原因**是：**当前迭代器所指向的元素被从容器中移除了（通过 `erase` 方法）**

对于 `unordered_set` 和 `unordered_map`，有一个额外的失效场景：**重哈希（Rehash）**。

- **什么是重哈希？** 当元素数量超过负载因子（load factor）阈值时，容器会自动创建一个更大的桶数组，并将所有现有元素重新计算哈希值并放入新的桶中。
- **影响**：**重哈希操作会使容器所有的迭代器失效**。不过，指向元素的**指针和引用仍然有效**（因为元素本身没有被移动或销毁，只是它在哈希桶中的位置改变了）。

你可以通过 `reserve()` 预先分配足够的桶来避免意外的重哈希，从而控制迭代器失效。



## 红黑树VS哈希表

STL中的哈希表通常使开链法，一个数组，每一个数组元素就是一个桶，指向的是一个链表：

1. 计算键的哈希值（通过 `std::hash` 函数）。
2. 根据哈希值和桶数组的大小，计算下标：`index = hash(key) % bucket_count()`。
3. 找到对应的桶（即数组中的那个位置）。
4. 遍历该桶下的链表：
   - 如果链表中已存在相同的键，则根据要求更新值或不做操作。
   - 如果不存在，则将新的键值对插入到链表中。

缺点：

- 哈希冲突：不同的键可能产生相同的哈希值，或者被映射到同一个桶中。在最坏情况下，如果所有键都冲突，哈希表会退化为一个链表，查找、插入、删除操作的时间复杂度变为 O(n)。
- 空间消耗较大：为了减少冲突，哈希表需要维持一定的“负载因子”（load factor，即元素数量 / 桶数量）。当元素增多时，需要扩容（rehash），即创建一个更大的桶数组并将所有现有元素重新哈希到新数组中。在这个过程中，哈希表占用的空间大约是实际数据大小的两倍

1. **解决哈希冲突**
   - **优秀的哈希函数**：使用分布均匀、随机性好的哈希函数。对于自定义类型，需要特化 `std::hash` 模板。对于基本类型，STL提供的哈希函数通常已经足够好。
   - **合适的桶数量**：使用 `reserve()` 函数预先分配足够数量的桶，避免插入过程中多次 rehash，也能减少冲突。`rehash(n)` 和 `max_load_factor(float z)` 也可以用来手动控制。
2. **优化空间消耗**
   - **预估数据量**：如果知道大致要存储的元素数量，提前使用 `reserve(n)` 预留空间，避免多次扩容，从而节省总体的空间消耗和时间开销。

## 解释函数对象

函数对象也称为 **仿函数** 是 C++ 中一种**行为类似函数的对象**，通过重载 `operator()` 实现。它既可以像普通函数一样被调用，又能存储状态（成员变量）
